# FORGE Product Plan

**Goal:** Take FORGE from the v0.1 bank-lending sandbox to a product a bank can pilot: first close v0.1, then make the sandbox evaluable by an outside engineer, then deepen lending, then add instruments, custody and markets.

**Source of truth:** the product decision and scope stay those of [FORGE MVP v0.1](../FORGE-MVP-v0.1.md): traditional banks first, Solana first, test assets only until a later phase says otherwise. This plan sequences the work after it; it does not widen the v0.1 scope.

**Evidence:** [validation.md](../validation.md), [prototype-walkthrough.md](../prototype-walkthrough.md), the 26-check `bun run e2e` run on a local validator (11 October 2026), and the October 2026 security audit with its fixes on PR #11.

## Phase 1 — A sandbox an outside bank can evaluate

The evaluation decides the order; these are the gaps already known.

| Work | Why |
| --- | --- |
| API keys: rotation, revocation, read-only and planning scopes, last-used time | Today a leaked key stays valid until someone edits the database. |
| Institution admin CLI: rotate keys, set or change the webhook URL, show delivery health | Every institution change is currently a database edit or a new institution. |
| Real signers in the console (Wallet Standard), browser-held demo keys only behind a demo flag | A shared demo must not keep signing keys in the browser. |
| OpenAPI description of the REST API, plus a Go or Java client example | The spec promises banks can integrate without TypeScript. |
| Pagination for statement, loans, withdrawals and vaults | Statements grow with every transfer, donations included. |
| Webhooks: attempt ceiling, dead-letter state, replay endpoint, delivery on its own loop | Retries are unbounded today, and a slow receiver delays everyone's tick. |
| Worker: an operator alert and a retry command for quarantined transactions | A transaction that fails three passes becomes an `unprocessable_transaction` exception and is skipped; retrying it means resetting the vault's cursors by hand. |
| Operator observability: structured logs, per-stage metrics, an operator-only status endpoint | Tenants no longer see worker errors; operators need them somewhere. |

**Exit:** a second evaluator integrates faster than the first, with fewer recorded failures, and names a workflow they would pilot.

## Phase 2 — Lending depth

Each program change gets an ADR, LiteSVM tests, an upgrade path for live Devnet accounts, and a re-run of the security audit on the changed instructions.

1. **Partial repayments and an accrual policy.** v0.1 fixes the payoff at proposal and accepts only full repayment. Choose the accrual model (whole-term or daily) with the evaluating bank; it changes the payoff calculation, the loan account and the statement postings.
2. **Cancellation and expiry.** Cancel an approved but undrawn loan, cancel a pending withdrawal, and reclaim rent from closed accounts. Deferred in [ADR 0003](../adr/0003-program-idempotency.md).
3. **Approver and treasury rotation.** Today a lost key means a new vault. Rotation needs both current approvers and must stay immutable per loan.
4. **Bind approvals to amounts.** `approve_withdrawal` takes no expected amount; add it, as `set_disbursement_paused` already does with its sequence.
5. **Pin the mint per institution.** `create_vault` accepts any six-decimal mint, freezable ones included; the API should register only the institution's approved mint.
6. **Borrower and issuer attestations.** Off-chain signed attestations (identity, credit decision) referenced by hash on the loan, without personal data on chain.
7. **Overdue events.** Overdue stays a computed view, but the worker should send `loan.overdue` when a loan crosses its due time, so the bank's collection process starts from a webhook.

**Exit:** a loan with partial repayments, cancellation and an attestation runs end to end on Devnet, and its statement reconciles.

## Phase 3 — Instruments, custody and production

1. **Token-2022 instruments with transfer rules.** The spec's separate milestone. The vault rules govern FORGE disbursements only; transfer restrictions on the instrument itself need Token-2022 extensions.
2. **Custody integration.** Banks sign through their custody provider (MPC or HSM) behind the same plan, verify and sign boundary; FORGE stays keyless (ADR 0002). Signer review must show the decoded intent, not only bytes.
3. **Production readiness.** An external audit of the program and services; a multisig or immutable upgrade authority; key custody for the deployer; legal review of how loans and instruments are described. Mainnet only after all of these.

## Phase 4 — Markets module

Hyperliquid and investment-market products, reusing institution identity, approvals and statements. No universal chain abstraction until a second chain is actually in use (spec §9).

## Running across phases

- **Security.** Re-audit after every program change and before Devnet demos to outside parties. Fixed findings keep their regression tests in `apps/api/test/security.test.ts` and `packages/sdk/sdk.test.ts`.
- **Evidence over claims.** Every phase exit is recorded in validation.md with commands and results, as v0.1's are.
- **Disclosure.** Test assets, fixture mint authority, upgrade authority and simulated bank systems stay disclosed wherever the product is shown.
